## 一、技术选型类

### Q1：为什么第一版用 Streamlit，后面又换成 Next.js 14？

**002 spec 明确记录**：

> "Streamlit 适合快速验证，但难以提供精致的 AI 产品体验。新增 Next.js 前端可显著提升品牌感，同时保留 Streamlit 作为故障回退。"

具体痛点在 002 User Story 中有说明：
- 视频播放需要流式修复（"浏览器无法直接播放本地路径"）
- 需要"更现代、更美观、交互更流畅的 Web 界面"

**不是预设策略，而是验证后的自然演进**。

---

### Q2：为什么用 SQLite 不用 PostgreSQL/MySQL？

**004 spec 背景**：

> "当前需分别启动后端 `run.py` 和前端 `npm run dev`，对非技术学生门槛过高。"

**设计目标**：降低使用门槛。SQLite 单文件零运维，配合 004 的"一键启动"脚本，让非技术用户也能跑起来。

---

### Q3：混合检索相比纯向量检索好在哪？

**002 spec User Story**：

> "混合检索提升 RAG 问答质量，全局搜索解锁'在所有已学课程中提问'的高阶场景"

> "用精确关键词提问时，混合检索能召回向量检索遗漏的内容"

**真实痛点**：向量检索对精确关键词不敏感，BM25 补充，RRF 融合。

---

### Q4：Playwright 做联网搜索，为什么不用搜索引擎 API？

**006 迭代一新增功能**（specs 中无独立文档，在 005 plan 的"第三迭代"中提及）。

真实原因：
- 免费搜索 API 不存在
- Playwright 驱动真实浏览器，抗反爬

**用户价值**：回答附"网络参考"区，来源可追溯。

---

### Q5：为什么做多模型配置？

**002 spec User Story**：

> "学习者希望为总结、问答、视觉理解分别配置最合适的模型"

> "多模型配置让系统在不同任务上取得成本与效果平衡"

**用户场景**：不同任务用不同模型，比如总结用便宜的，问答用效果好的。

## 二、算法与实现类

### Q6：SM-2 间隔重复算法是怎么实现的？

**005 spec**：

> 闪卡复习："简单三档标记（认识/模糊/不认识），SM-2 间隔重复留后续"

**006 迭代一实现**：
- ease（难度系数，初始 2.5）
- interval（间隔天数）
- due_date（到期时间）
- quality 0-5 评分驱动调度

**用户价值**：只复习到期的卡片，不用每天翻全部。

---

### Q7：RAG 引用角标是怎么保证准确的？

**真实踩坑**（git 历史）：

> "引用堆砌 [1][2][3][4][5]" → 后端 `_cap_consecutive_citations` 硬截断 ≤3

**实现**（代码可查）：
- LLM 标 [MM:SS] 时间戳
- 后端映射稳定 [N] 序号
- 正文 [N] = 来源第 N 条

**设计意图**：来源可追溯，防止 LLM 编造。

---

### Q8：faster-whisper 怎么防止幻觉？

**真实实现**（代码可查）：
- VAD（语音活动检测）跳过非语音段
- 禁用上下文传递（condition_on_previous_text=False）
- OpenCC 繁→简转换

**002 spec**："处理速度直接影响首次使用体验"，所以用 int8 量化加速。

---

### Q9：测验题是 LLM 生成的，怎么保证质量？

**005 spec**：

> "题型：第一版只做选择题 + 判断题（可自动判分）；简答题留到后续迭代（需 LLM 判分）"

> "解决'看完就忘、不知道自己掌握没'的最高频痛点"

**实现**：
- LLM 生成结构化 JSON（题干、选项、答案、解析）
- 后端 schema 校验
- 判分直接比对选项，不依赖 LLM

## 三、工程与挑战类

### Q10：faster-whisper 在 CPU 上很慢，怎么解决？

**002 spec**：

> "学习者上传 45 分钟课程后，不希望等待 10-20 分钟才能完成处理"

**优化**（002 US2 帧处理加速）：
- 智能视觉调用（OCR 能解决的不用视觉模型）
- 并行 API 调用
- 场景变化抽帧

**后续优化**（git 历史）：
- 断点续传：重新处理复用 ASR 字幕

---

### Q11：项目最大的技术挑战是什么？

**真实踩坑**（git 历史 + 展示页）：

1. **字幕重复显示**：浏览器 controls+track 渲染两次 → track hidden + JS 自绘
2. **联网搜索卡死 90 秒**：Playwright sync 在 FastAPI 线程池 event loop 冲突 → 子进程隔离
3. **重新处理等 40 分钟**：`_clear_old_course_data` 清掉 ASR 字幕 → 断点续传

**每个坑都有真实的用户痛点**。

## 附录：完整技术栈详解

### 后端框架

**FastAPI + Uvicorn**
- **选择原因**：FastAPI 自动生成 OpenAPI 文档，类型提示驱动，异步原生支持；Uvicorn 是高性能 ASGI 服务器
- **优点**：开发效率高、自动文档、类型安全、异步性能好
- **缺点**：生态不如 Flask/Django 成熟，某些复杂场景需要手动处理

**Pydantic + SQLModel**
- **选择原因**：Pydantic 是 Python 数据校验的事实标准；SQLModel 由 FastAPI 作者开发，ORM 和 Pydantic 模型一体，减少重复代码
- **优点**：模型/校验一体、类型提示完整、与 FastAPI 无缝集成
- **缺点**：SQLModel 相对较新，复杂查询不如 SQLAlchemy 灵活

**SQLite**
- **选择原因**：004 spec 明确"降低使用门槛"，单文件零运维，用户下载即用
- **优点**：零配置、单文件备份、足够个人使用、Python 内置支持
- **缺点**：并发写性能一般、不适合多实例部署、网络存储性能差

---

### AI 能力

**faster-whisper（CPU int8）**
- **选择原因**：OpenAI Whisper 的 CTranslate2 加速版，本地运行保护隐私；int8 量化在 CPU 上速度提升 4 倍
- **优点**：本地免费、隐私安全、多语言支持、VAD 反幻觉、可离线运行
- **缺点**：CPU 慢（1 小时视频需 20-40 分钟）、大模型内存占用高、准确率略低于云端 API

**OpenCC**
- **选择原因**：港台课程视频转写常输出繁体，简体用户阅读困难
- **优点**：开源免费、繁简转换准确、支持词汇级转换
- **缺点**：增加处理步骤、极个别专业术语转换不准

**ffmpeg-python**
- **选择原因**：视频处理事实标准，Python 封装简洁，提取音轨供 ASR 使用
- **优点**：功能强大、格式支持全面、社区成熟
- **缺点**：依赖系统 ffmpeg 安装、大视频处理内存占用高

**PaddleOCR + OpenCV**
- **选择原因**：PaddleOCR 中文识别准确率业界领先；OpenCV 视频抽帧稳定高效
- **优点**：中文识别准、支持表格/公式、OpenCV 跨平台稳定
- **缺点**：PaddlePaddle 依赖重、安装复杂、GPU 版本配置麻烦

**视觉 LLM（GPT-4V/DeepSeek-VL 等）**
- **选择原因**：002 spec "复杂帧才调视觉模型省成本"，OCR 无法理解的图表/公式/代码用视觉模型
- **优点**：理解能力强、可解释复杂视觉内容、多模型可切换
- **缺点**：调用有延迟、按 token 收费、需要网络

**edge-tts**
- **选择原因**：微软 Edge 浏览器在线 TTS，音色自然，免费额度高，支持中文多音色
- **优点**：音色自然、免费、多语言、多音色可选
- **缺点**：需联网、有调用频率限制、依赖微软服务稳定性

---

### RAG 检索

**LangChain**
- **选择原因**：RAG 生态最成熟的框架，封装检索流程，链式调用清晰
- **优点**：生态丰富、文档齐全、社区活跃、抽象层次合理
- **缺点**：版本迭代快、API 变动频繁、部分封装过度抽象

**Chroma + sentence-transformers**
- **选择原因**：Chroma 轻量级向量数据库，嵌入式部署；sentence-transformers 生成高质量中文嵌入
- **优点**：Chroma 零配置、本地运行；sentence-transformers 中文效果好、HuggingFace 模型丰富
- **缺点**：Chroma 大规模性能一般；sentence-transformers 首次下载模型慢

**BM25 + jieba**
- **选择原因**：002 spec "用精确关键词提问时，混合检索能召回向量检索遗漏的内容"；jieba 中文分词准确
- **优点**：BM25 关键词匹配精准、无需训练、速度快；jieba 中文分词成熟
- **缺点**：BM25 无语义理解；jieba 新词发现能力有限

**RRF（Reciprocal Rank Fusion）**
- **选择原因**：融合双路召回结果，不需要调权重，效果稳定
- **优点**：无需调参、实现简单、效果稳定
- **缺点**：无法利用分数绝对值、对异常值敏感

**OpenAI API + httpx + tenacity**
- **选择原因**：OpenAI API 是 LLM 事实标准；httpx 异步 HTTP 客户端性能高；tenacity 自动重试提高稳定性
- **优点**：OpenAI 模型效果好、生态成熟；httpx 异步支持好；tenacity 重试策略灵活
- **缺点**：OpenAI 收费、国内访问需代理；httpx 学习曲线；tenacity 配置不当可能过度重试

---

### 前端框架

**Next.js 14 + React 18 + TypeScript**
- **选择原因**：002 spec "Streamlit 难以提供精致的 AI 产品体验"；Next.js SSR 防闪跳，App Router 现代路由，TypeScript 类型安全
- **优点**：SSR 首屏快、App Router 文件即路由、TypeScript 减少运行时错误、生态丰富
- **缺点**：学习曲线陡、构建配置复杂、App Router 文档不够完善

**TanStack Query**
- **选择原因**：服务端状态管理最佳实践，缓存、同步、失效策略完善
- **优点**：缓存智能、自动重试、乐观更新、开发者工具强大
- **缺点**：概念较多、学习成本高、小包体积较大

**Radix UI + Tailwind CSS**
- **选择原因**：Radix 无样式组件可完全定制；Tailwind 原子化 CSS 开发效率高
- **优点**：Radix 无障碍支持好、无样式限制；Tailwind 开发快、一致性好
- **缺点**：Radix 需要自己写样式；Tailwind 类名冗长、HTML 可读性差

**Framer Motion + react-markdown + lucide-react**
- **选择原因**：Framer Motion 动画流畅；react-markdown 渲染 AI 回答；lucide 图标统一美观
- **优点**：Framer Motion 声明式动画、性能好；react-markdown 插件丰富；lucide 图标风格统一
- **缺点**：Framer Motion 包体积大；react-markdown 定制样式麻烦；lucide 图标数量有限

---

### 扩展功能

**Playwright（子进程）**
- **选择原因**：真实浏览器渲染，抗反爬能力强；子进程避免 FastAPI event loop 冲突（真实踩坑）
- **优点**：真实浏览器、支持 JS 渲染、多浏览器支持、截图/PDF 功能强
- **缺点**：资源占用高、速度慢、部署需下载浏览器

**yt-dlp + httpx**
- **选择原因**：yt-dlp 支持 1000+ 视频平台；httpx 处理内网直链（SSL 宽容）
- **优点**：yt-dlp 平台覆盖广、更新频繁；httpx 异步支持、SSL 配置灵活
- **缺点**：yt-dlp 对国内平台支持不稳定；httpx SSL 宽容有安全风险

---

### 测试

**pytest + pytest-asyncio**
- **选择原因**：Python 测试事实标准，pytest-asyncio 支持异步测试
- **优点**： fixture 强大、插件丰富、断言简洁、异步支持好
- **缺点**：学习曲线、fixture 作用域复杂、并行测试配置麻烦

---

### 旧版（已归档）

**Streamlit + streamlit-player + stqdm**
- **选择原因**：001 版本快速验证，Python 生态内最快搭建 Web UI 的方案
- **优点**：开发极快、Python 原生、适合数据科学原型
- **缺点**：交互能力弱、状态管理差、不适合复杂应用、每次交互整页刷新

**保留原因**：002 spec "保留 Streamlit 作为故障回退"
